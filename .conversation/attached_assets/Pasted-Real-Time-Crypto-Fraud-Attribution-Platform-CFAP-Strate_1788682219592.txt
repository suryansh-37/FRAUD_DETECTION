Real-Time Crypto Fraud Attribution Platform (CFAP)
Strategic Blueprint — Roles, Features, Workflows & Edge Cases
1. Core Idea in One Line

A single platform that takes a victim-reported wallet address (from NCRP/complaint), automatically traces it on-chain, identifies the VASP/exchange holding the funds, and auto-generates the legal request to that VASP via a SAHYOG-style notice module — cutting the time between "complaint filed" and "freeze request sent" from days to minutes.

Two engines working together:

Hornet-style engine → blockchain tracing, entity attribution, risk scoring
SAHYOG-style engine → structured legal notice generation, VASP response tracking, inter-agency coordination
2. User Personas & Login Types

Think of this as 6 distinct login roles, each seeing a different dashboard. This is the most important design decision — one dashboard for everyone will fail in a real deployment.

🔵 Role 1: Investigating Officer (IO) — District/State Cyber Cell

Who: The police officer actually working the case.

What they do on login:

See a list of cases assigned to them (auto-pulled from NCRP/CFCFRMS once linked)
Paste/import a wallet address → click "Trace"
View the fund-flow graph (wallet → hops → mixer/bridge → exchange)
See risk score (System Score + AI Score, like Hornet's dual-engine)
One-click "Generate VASP Notice" → auto-fills a SAHYOG-style legal request with case ID, wallet, amount, exchange name, legal section (BNSS 94 / IT Act 79(3)(b))
Track notice status: Sent → Acknowledged → Data Received → Freeze Confirmed
Download a court-ready investigation report (PDF, chain-of-custody stamped)
Get push alerts if the traced wallet moves again after the case is opened

Edge cases for this role:

Officer has zero blockchain knowledge → UI must explain findings in plain language ("This wallet sent 2.4 ETH to Binance in 3 hops"), not just show a raw graph
Multiple complaints point to the same wallet (common in organized fraud) → system must auto-detect and merge/link cases, not create duplicate notices to the same VASP
Officer works a case with no confirmed exchange found (funds still in a non-custodial wallet) → system should still allow "watchlist" mode with auto-alert when it finally moves
🟢 Role 2: Nodal Officer / State Cyber Cell Supervisor

Who: Reviews and approves before anything goes external (to a VASP or another state).

What they do:

Dashboard of all cases in their state/unit — filterable by risk level, fraud type, amount, status
Approve or reject VASP notices before they're sent (prevents junior officers from sending bad/duplicate requests)
Reassign cases across officers/districts
See cross-jurisdiction matches — e.g., same wallet flagged in Telangana and West Bengal simultaneously → triggers coordination workflow (this maps directly to the "Samanvaya" cross-state coordination need)
Analytics: fraud typology trends, top exchanges receiving illicit funds, average freeze time

Edge cases:

Two states independently trace the same wallet/case → needs de-duplication + auto-merge with both officers linked, not silent conflict
Supervisor is on leave/unavailable → escalation timer auto-routes approval to a backup approver (a stuck approval = a fraudster's window to move funds)
🟠 Role 3: National Coordination Admin (I4C-level)

Who: Oversees the whole system across states, manages VASP relationships nationally.

What they do:

National heatmap: fraud hotspots, top wallets, top VASPs by volume of flagged funds
Manage the master VASP directory (which exchanges are onboarded to receive notices, their compliance contacts, SLA response times) — this is essentially the SAHYOG-side function
Publish suspect wallet registry shared across all states (so a wallet flagged in one FIR is instantly visible nationwide — like the Suspect Registry concept)
Manage integration health: NCRP feed status, blockchain node/API status, VASP API status
Generate policy-level reports (₹ recovered, average TAT, VASP compliance ranking)

Edge cases:

A VASP never responds or is unresponsive/foreign and uncooperative → system needs an escalation path (e.g., auto-flag to FIU-IND / MHA international cooperation channel) rather than a dead end
Fake/spoofed complaint data entering from NCRP → validation layer before it hits the tracing engine
🟣 Role 4: VASP / Exchange Compliance Officer (External Login)

Who: The exchange's own compliance team, logging in from their side.

What they do:

Receive the notice/freeze request directly on this portal (instead of email/PDF chase)
View only the specific case's wallet + minimum necessary legal basis (never full case file — privacy/least-privilege)
Respond with: KYC data / account freeze confirmation / "not our wallet" / request more info
Legally-timestamped audit trail of their response time (protects both sides — VASP proves compliance, LEA proves request was sent)

Edge cases:

Wallet belongs to a foreign exchange with no India presence → system should still identify it (for intelligence) but clearly flag "no legal jurisdiction — refer to international MLAT/Interpol channel" instead of pretending a notice will work
VASP disputes attribution ("this isn't our wallet") → dispute/appeal flow needed, not just accept/reject binary
⚫ Role 5: System/Platform Admin

Who: Technical admin — not police, manages the platform itself.

What they do:

User provisioning (create/deactivate officer logins, role assignment)
API key management (blockchain data providers, NCRP feed, VASP APIs)
Monitor system uptime, data pipeline health, model retraining status for the AI risk engine
Manage audit logs (who accessed which case — critical for evidence integrity in court)

Edge cases:

An officer transfers departments → access must auto-revoke/transfer, old case access logged but not open-ended
Data retention rules differ by state/case type → configurable retention, not one global rule
🟡 Role 6: Auditor / Legal Reviewer (Optional but strong for SIH scoring)

Who: Checks that evidence is court-admissible.

What they do:

Independently verify a case's chain-of-custody log (every trace, every notice, every timestamp, immutable)
Sign off on reports before they go to court
Flag any report where the tracing methodology needs to be explained under cross-examination

Edge cases:

AI risk score contributed to the investigation lead, but AI outputs generally aren't admissible as sole evidence → report must clearly separate "AI-assisted leads" from "verifiable on-chain facts," so the auditor can certify only the latter as evidence.
3. End-to-End User Journey (The Actual Flow)
Victim files complaint on NCRP
        ↓
Wallet address auto-extracted & ingested into CFAP
        ↓
System auto-traces (multi-chain) → builds fund-flow graph
        ↓
Risk engine scores wallet (rules + AI) → flags exchange/VASP endpoint
        ↓
Case auto-assigned to IO based on jurisdiction
        ↓
IO reviews → Supervisor approves → Notice auto-generated (SAHYOG-style)
        ↓
Notice sent to VASP portal login
        ↓
VASP responds (freeze/KYC data/dispute)
        ↓
Funds frozen / evidence preserved → Case updated
        ↓
Court-ready report generated → Auditor certifies → Victim fund recovery process begins
4. Edge Cases Master List (Group by Category)

Technical / Blockchain

Privacy coins (Monero) or heavily mixed transactions → tracing may hit a dead end; system must say "trace inconclusive beyond hop X" honestly, not fabricate confidence
Cross-chain bridges/DEXs breaking the trail → need bridge-specific decoding logic per chain pair
New/unsupported blockchain used by fraudster → graceful "unsupported chain" flag, not silent failure
Blockchain API/node downtime → cached last-known state + retry queue, never silently drop a trace request

Legal / Jurisdictional

Wallet traces to an exchange outside India with no treaty → route to MLAT/international cooperation, not a dead click
Multiple states claim jurisdiction on one case → single source of truth + coordination workflow (as above)
Notice format must map to correct legal section depending on case type (fraud vs. ransomware vs. terror financing may cite different provisions)

Data / Case Management

Duplicate complaints for the same fraud ring → auto-clustering, not N separate cases to N separate officers
False positive risk scores → officer must be able to see why a score was given (explainable, not a black box), and dispute/correct it
Wallet reused across unrelated old cases → system should show historical linkage, but not auto-merge unrelated cases blindly

Security / Trust

Chain of custody must be tamper-evident (immutable logs) or the report is useless in court
VASP portal is an external-facing login → strictest access control, since it's the platform's biggest attack surface
Insider misuse (an officer looking up unrelated wallets out of curiosity) → full audit trail + anomaly detection on internal usage too

Operational

Officer with low technical literacy → UI defaults to plain-language summaries, graph view is optional/advanced
Alert fatigue — if every wallet movement pings the officer, they'll ignore alerts → prioritize/tier alerts by risk score and case severity
Scale — thousands of complaints/day nationally → indexing and tracing must be async/queued, not real-time-blocking on complaint submission
5. Strategic Build Roadmap (for SIH Judging)
Phase	Focus	Why it matters for judges
Phase 1 – MVP	Single-chain (ETH/BTC) tracing + risk scoring + IO dashboard + manual notice draft	Proves core tracing works — this is the technical core
Phase 2 – Multi-role	Add Supervisor approval flow + VASP portal + notice automation	Shows the "attribution → action" loop, which is the actual SIH ask
Phase 3 – Integration	Real/simulated NCRP feed ingestion + cross-state case linking (Samanvaya-style)	Shows systemic thinking beyond just a tracing tool
Phase 4 – Intelligence layer	AI risk model, fraud-typology tagging (scam/sextortion/ransomware), analytics dashboard	Differentiator — most competing teams will stop at Phase 1

What will make your submission stand out: most teams will build "just a tracer." Judges will specifically look for the VASP notice automation + multi-role approval workflow — because that's the actual bottleneck named in the problem statement ("inability to quickly identify... delays freezing"). Lead your pitch with that, not with the blockchain graph visual.

6. Quick Answer to "What does the user actually consume?"
Police officer: a case list + a trace button + a plain-language verdict + a one-click notice
Supervisor: an approval queue + cross-jurisdiction radar
National admin: a national map + VASP compliance scoreboard
Exchange: a clean inbox of legally valid requests, nothing more
Auditor: a certified, immutable trail
Admin: a control panel for users, keys, and uptime

Each role should feel like a different, purpose-built app — not the same dashboard with different permissions bolted on.
